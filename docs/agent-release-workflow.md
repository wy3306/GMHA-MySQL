# Agent 版本发布与推送升级

修改代码不会自动改变已运行的 Agent。每次修复完成后，需要构建发布一个新的制品版本，再推送到目标机器。

## 源码部署

在「Agent 管理」点击「构建并发布新版本」。平台异步构建 Linux AMD64 和 ARM64，自动选择高于已发布版本的版本号，通过构建参数写入二进制，登记版本、架构和 SHA-256。页面自动轮询并显示新版本与可升级数量。构建失败保留任务错误，不会把单架构编译成功误报为完整发布。

命令行采用同一构建流程，在源码根目录运行：

```sh
./scripts/build-agent.sh
```

默认读取当前用户 `~/.gmha/package-store.json`，使用 Manager 的制品存储目录；自定义 Manager 状态目录时传 `--settings /path/to/package-store.json`。远程构建机可以传 `--storage /path/to/output`，然后将两份 `.bin` 上传至目标平台的 Agent 制品库。指定 storage 不会改变现有 Manager 的存储配置。

构建进程在仓库中使用 `.agent-build.lock` 排除重复构建。进程被强制终止后若残留锁，须确认没有构建仍在执行，再删除该空锁目录。

## 二进制部署

没有源码或 Go 工具链时，平台提示上传预构建制品。将两种架构相同版本的文件上传，版本比较和升级提示会自动刷新。完整发行脚本 `scripts/build-release.sh` 不再使用固定默认版本号；不传版本时根据已发布及 dist 现有版本递增。显式传入版本仍应保证唯一，不要用相同版本号发布不同内容。

## 推送行为与确认

- Agent 任务通道在线时，平台通过 Agent 自身下载、校验并安排独立 systemd 临时单元完成升级，不要求 Manager 能访问目标机 SSH 端口。这样可处理 `dial tcp <IP>:22: i/o timeout`。
- Agent 任务通道离线时使用 SSH 兜底；此时 Manager 必须能连接目标机器配置的 SSH 端口。任务通道和 SSH 都不可用时不会声称已经推送。正在安装的目标暂不可选。
- 批量选择一个版本，Manager 为每台机器匹配同版本、对应架构的制品，缺少制品会在替换前失败。
- 单机升级使用仓库中该架构的最新版本，不再将旧版本号作为升级目标。
- 上传候选文件后先在目标机执行 `--version`。版本不匹配或无法执行时，不替换运行文件。
- 重启后核对新鲜心跳及实际版本。版本记录在确认后更新，失败不会提前标记为目标版本；失败回退通过临时文件原子替换旧程序。
- 同版本和降级仍不允许作为正常升级提交。版本未知时先使用版本检测读取目标机器的真实版本。

本次生成的 V0.3.2 包含 Agent 启动重连、轮转压缩日志、版本发布管理和在线任务通道升级修复。远端平台需要先部署包含本次修复的 Manager，才能在 SSH 入站不可用时使用 Agent 在线推送；本地构建不会自动替换远端服务。
